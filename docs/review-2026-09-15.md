## Cross-cutting notes and ordering

- Delivery has two independent contracts: replay must be gap-free and duplicate-free, and queue overflow must terminate a subscription. Fix `EC-002` before `EC-003`; otherwise an overflow reconnect can still duplicate the boundary event.
- Input has three layers (`webInput`, daemon queueing, `Agent.Run`) that currently disagree about acceptance. Fix `EC-001` and `EC-005` together or in that order, preserving image ownership across queueing.
- Web listener publication is a state machine. Fix `EC-004` before `EC-011`; cleanup added for an unexpected `Serve` exit must not race publication or clear a newer listener.
- MCP ordinary tool calls already contain the desired timeout/reconnect policy. `EC-007` should land before `EC-015`, then the latter should reuse that policy rather than cloning it a third time.
- Three areas hand-roll bounded protocol parsing. The OpenAI parser should borrow the already-correct event accumulator in `internal/provider/codex.go`, not introduce another SSE abstraction.
- Keep fixes boring and standard-library-only. None of these tickets justifies a new dependency.

## Findings

### EC-001 — Image-only input is dropped and its images leak into the next turn

- Severity / Area / Difficulty / Files: P1 / agent, daemon input / S / `internal/agent/agent.go` (`run`), `internal/daemon/webcmd.go` (`webInput`), agent tests.
- Problem: the web API explicitly accepts an image with empty text (`internal/daemon/webcmd.go:149-154`), and the daemon attaches it before calling `Run` (`internal/daemon/server.go:1766-1778`). `Agent.run`, however, consumes `pendingImages` only inside `if strings.TrimSpace(userInput) != ""` (`internal/agent/agent.go:501-512`). The image-only turn therefore calls the provider with old history and leaves the image staged for a later prompt. Whitespace-only text has the same phantom-turn behavior.
- Evidence: disposable `TestReviewImageOnlyTurnConsumesItsAttachment` failed with the image attached to the next prompt: `go test ./internal/agent -run TestReviewImageOnlyTurnConsumesItsAttachment -count=1 -v`.
- Why it matters: the requested image is not analyzed; worse, it can be disclosed to a later, unrelated prompt and persisted under the wrong user message.
- Suggested fix: under `a.mu`, atomically take `pendingImages` for every accepted run. Append a user message when text is nonblank **or** images are present. Call recall only for nonblank text. Reject whitespace-only/no-image input at HTTP and socket-facing validation.
- Verification: add the named regression test following `agent_test.go` conventions, then run `go test -race ./internal/agent -run 'Test(ImageOnly|Attach)' -count=1` and `go test ./internal/daemon -run 'TestWebInput' -count=1`.
- Pitfalls: do not read and clear `pendingImages` in separate critical sections; concurrent attachment is already documented in the adjacent comment. Preserve `Hidden` and image-only persistence.
- Do-not: do not synthesize magic prompt text or change provider image encoding.

### EC-002 — Attach and SSE replay can deliver the boundary event twice

- Severity / Area / Difficulty / Files: P1 / daemon transport / M / `internal/daemon/server.go` (`MsgAttach`), `internal/daemon/webapi.go` (`webEvents`), ring/transport tests.
- Problem: both paths subscribe first and then independently snapshot the ring (`internal/daemon/server.go:2367-2381`, `internal/daemon/webapi.go:238-284`). An event published between those operations is present both in replay and in the live subscriber channel.
- Evidence: deterministic disposable `TestReviewSubscribeBeforeReplayDoesNotDeliverSameEventTwice` inserted one event after subscribe and found sequence 1 in both sources: `go test ./internal/daemon -run TestReviewSubscribeBeforeReplayDoesNotDeliverSameEventTwice -count=1 -v`.
- Why it matters: reconnecting clients can render duplicate deltas/tool rows and apply lifecycle events twice. Moving subscribe after replay would exchange this bug for lost events.
- Suggested fix: capture a replay high-water sequence after subscription. Send ring entries through that sequence, then discard queued live `MsgEvent`s with `Seq <= highWater`. Apply identical semantics to socket and SSE, preferably through a small shared attach helper.
- Verification: add deterministic tests for event-before, event-during, and event-after the boundary to `internal/daemon`; run `go test -race ./internal/daemon -run 'Test.*(Attach|Replay|WebEvents)' -count=20`.
- Pitfalls: snapshots and non-event messages have no comparable event sequence; do not discard them. Preserve the no-gap property.
- Do-not: do not reorder to replay-before-subscribe.

### EC-003 — Full subscriber queues silently lose events without reconnecting

- Severity / Area / Difficulty / Files: P1 / daemon, SSE / M / `internal/daemon/server.go` (`broadcast`, subscription type), `internal/daemon/webapi.go` (`webEvents`), tests.
- Problem: `broadcast` uses a nonblocking send and does nothing in `default` (`internal/daemon/server.go:1451-1462`). The subscriber stays connected, so it never replays the skipped sequence. The SSE comment incorrectly says the client is disconnected (`internal/daemon/webapi.go:205-212`). Existing `TestWebEventsSlowClientDoesNotStallTheSession` publishes 2,000 events and expects the subscriber to remain live, pinning loss rather than recovery.
- Evidence: code proof plus the contradictory test. This is **known, new evidence** relative to `docs/codex_review2.md` R2-02: that review noted the 256-item queue's memory shape, but not that overflow violates the documented drop-close contract in `docs/plan-web.md:176` and `:346-347`.
- Why it matters: a temporarily slow browser or terminal silently develops a permanently incomplete transcript while appearing healthy.
- Suggested fix: represent a subscription with data plus an overflow/done signal. Under `sess.mu`, mark/remove it on the first full send; the socket relay/SSE loop must exit so reconnect replay repairs the gap. Avoid closing a channel that a copied broadcaster may still send to.
- Verification: replace the current slow-client assertion with a test that fills the queue, observes stream termination, reconnects with the last delivered sequence, and receives the gap. Run `go test -race ./internal/daemon -run 'Test.*SlowClient' -count=20`.
- Pitfalls: fix `EC-002` first. Ensure `Clients` decrements once and idle-watchdog activity remains correct.
- Do-not: do not increase the buffer or block `publishEvent` on client I/O.

### EC-004 — `ListenWeb` publishes a partially initialized `webState`

- Severity / Area / Difficulty / Files: P1 / daemon concurrency / S / `internal/daemon/web.go` (`ListenWeb`), tests.
- Problem: `s.web = w` is published under `s.mu` at `internal/daemon/web.go:100-121`, but `w.srv` is assigned later without the lock at `:123-127`. `Server.Close` reads `web.srv` at `internal/daemon/server.go:650-681` under a different synchronization history.
- Evidence: disposable `TestReviewListenWebDoesNotPublishPartialState` under `go test -race ./internal/daemon -run TestReviewListenWebDoesNotPublishPartialState -count=1` reported writes at `web.go:127` racing reads at `server.go:677`, including access to the partially built `http.Server`.
- Why it matters: concurrent startup/shutdown can race, fail to close the HTTP server, or access partially initialized state.
- Suggested fix: build the mux and `http.Server`, assign `w.srv`, then publish the fully initialized `w` under `s.mu`; start `Serve` only after publication. Close the listener on every refused publication path.
- Verification: retain a barrier-based race test and run it 50 times under `-race`, plus `go test -race ./internal/daemon -run 'Test.*Web.*Close' -count=10`.
- Pitfalls: `w.mux(s)` reads config/theme through server methods; do not hold `s.mu` while building it.
- Do-not: do not solve this with a second mutex inside `webState`.

### EC-005 — Web acknowledges prompts that the daemon rejected

- Severity / Area / Difficulty / Files: P1 / daemon input / M / `internal/daemon/server.go` (`inputRequest`), `internal/daemon/webcmd.go` (`webInput`), socket handler, tests.
- Problem: `inputRequest` has no result. It returns silently while closing and emits only an asynchronous notice when the bounded queue is full (`internal/daemon/server.go:1707-1753`). `webInput` then unconditionally writes `{"ok":true}` (`internal/daemon/webcmd.go:153-154`).
- Evidence: disposable `TestReviewWebInputDoesNotAckRejectedQueueEntry` filled `MaxQueuedInputs`; the next POST still returned success: `go test ./internal/daemon -run TestReviewWebInputDoesNotAckRejectedQueueEntry -count=1 -v`.
- Why it matters: the browser clears a prompt that was never queued. This is user-authored data loss with no reliable recovery.
- Suggested fix: make `inputRequest` return a small status or error (`started`, `queued`, `queue full`, `closing`). Map full to HTTP 429 or 409 and closing to 409. Have the socket handler send `MsgError` on immediate refusal.
- Verification: add HTTP tests for started, queued, full, and closing; run `go test -race ./internal/daemon -run 'Test.*Input' -count=10`.
- Pitfalls: only acknowledge after image bytes are owned by the queue/turn. Keep asynchronous notices for attached observers, but do not use them as the request response.
- Do-not: do not remove queue bounds or change normal FIFO ordering.

### EC-006 — `write` overwrites an existing file after its required pre-read fails

- Severity / Area / Difficulty / Files: P1 / filesystem tools / S / `internal/tools/fs.go` (`writeTool`), tests.
- Problem: the tool reads existing content for its diff, handles only success and `ErrNotExist`, and ignores every other error (`internal/tools/fs.go:810-816`). It then atomically replaces the file at `:817-821`. An unreadable file is treated as empty-but-existing.
- Evidence: disposable `TestReviewWriteDoesNotReplaceUnreadableExistingFile` created a mode-0200 file in a writable directory. `go test ./internal/tools -run TestReviewWriteDoesNotReplaceUnreadableExistingFile -count=1 -v` failed because write succeeded after the required read failed.
- Why it matters: permission/transient I/O errors turn a safe edit into blind data destruction, and the shown diff falsely claims the old file was empty.
- Suggested fix: return a wrapped error for every pre-read failure except `os.ErrNotExist`; do not create parents or write after that point.
- Verification: add the regression to `fs_edit_test.go` or `tools_test.go`; run `go test ./internal/tools -run 'Test.*Write.*(Unreadable|Atomic|Confine)' -count=1`.
- Pitfalls: run the permission test as a non-root user or use an injectable read seam; root can read mode-0200 files. Preserve the create-new path.
- Do-not: do not fall back to an empty diff.

### EC-008 — Successful extraction discards transcript turns never sent to the router

- Severity / Area / Difficulty / Files: P1 / memory / M / `internal/memory/pipeline.go` (`peekTranscript`, `Extract`, `clearTranscript`), tests.
- Problem: `Extract` records the count of the entire accumulated transcript (`internal/memory/pipeline.go:520-525`) but sends only `Truncate(text, 12000)`. On success it clears all `n` original turns (`:561-565`), including the suffix the router never received.
- Evidence: disposable `TestReviewExtractRetainsTurnsBeyondPromptLimit` failed: `go test ./internal/memory -run TestReviewExtractRetainsTurnsBeyondPromptLimit -count=1 -v` reported that a successful extraction discarded an unseen turn.
- Why it matters: durable preferences/projects mentioned after the byte cutoff can be permanently forgotten even though extraction reports success.
- Suggested fix: dequeue a bounded batch and return the exact count represented in it. Prefer whole turns up to 12,000 bytes. Define an explicit oversized-single-turn policy: chunk it and retain the remainder, or send a rune-safe prefix and retain a suffix.
- Verification: tests must cover multiple turns crossing the cap, one oversized turn, turns appended during extraction, provider failure, and store failure; run `go test -race ./internal/memory -run 'Test.*Extract' -count=10`.
- Pitfalls: `extractMu` serializes extraction, but `ObserveTurn` may append concurrently; clear only the submitted prefix.
- Do-not: do not merely raise the 12,000-byte cap.

### EC-009 — OpenAI-compatible parser rejects valid multiline SSE events

- Severity / Area / Difficulty / Files: P2 / provider streaming / M / `internal/provider/openai.go` (`streamOpenAISSE`), tests.
- Problem: the parser treats every `data:` line as a complete JSON document (`internal/provider/openai.go:436-459`). SSE defines an event as all `data:` fields up to the blank line; their values are joined with newlines. The Codex adapter already implements accumulation at `internal/provider/codex.go:877-904`.
- Evidence: disposable `TestReviewOpenAISSEJoinsMultipleDataLines` split valid JSON across two `data:` fields; `go test ./internal/provider -run TestReviewOpenAISSEJoinsMultipleDataLines -count=1 -v` failed with an unexpected-end JSON error.
- Why it matters: compliant gateways/proxies that fold a large event can abort otherwise valid streams.
- Suggested fix: accumulate data fields, dispatch on blank line and EOF, ignore comments/other fields, and recognize `[DONE]` after assembly. Adapt the Codex logic locally.
- Verification: add multiline, CRLF, comment, EOF-without-final-blank, `[DONE]`, malformed-event, and existing tool-fragment tests; run `go test ./internal/provider -run 'Test.*(OpenAI|SSE)' -count=1`.
- Pitfalls: do not use `TrimSpace` on each data value; SSE removes at most the optional single leading space and preserves meaningful payload whitespace.
- Do-not: do not merge the OpenAI and Codex response schemas.

### EC-010 — Failed web bind can orphan a newly minted token and suppress its URL

- Severity / Area / Difficulty / Files: P2 / web startup / S / `internal/daemon/web.go` (`ListenWeb`), tests.
- Problem: token creation happens before `net.Listen` (`internal/daemon/web.go:81-95`). If bind fails, the new token file remains. A later successful start loads it with `minted=false`, so `WebInfo.Minted` is false and startup will never print the one-time tokenized handoff URL (`internal/daemon/web.go:281-310`).
- Evidence: direct control-flow proof. Existing bind-failure coverage checks only that the Unix socket survives, not token lifecycle.
- Why it matters: first-time web setup can leave the user with an authenticated listener but no displayed browser URL.
- Suggested fix: bind first, then mint/load the token; close the listener if token setup fails. This also avoids filesystem changes for an address that cannot start.
- Verification: occupy a port, call `ListenWeb`, assert no token file; release it and start successfully, assert `WebInfo.Minted`; run `go test ./internal/daemon -run 'Test.*Web.*(Bind|Token)' -count=1`.
- Pitfalls: preserve a pre-existing token on bind failure and close every newly opened listener on later error.
- Do-not: do not delete an existing token file as rollback.

### EC-011 — Unexpected HTTP `Serve` exit leaves stale advertised state

- Severity / Area / Difficulty / Files: P2 / web lifecycle / M / `internal/daemon/web.go` (`ListenWeb`, `WebInfo`), tests.
- Problem: the serving goroutine discards `srv.Serve(ln)`'s result (`internal/daemon/web.go:128-132`). On an unexpected listener failure, `s.web` remains non-nil; `WebInfo` advertises a dead address and another `ListenWeb` is refused as already listening.
- Evidence: direct state-machine proof: only `Server.Close` clears `s.web` (`internal/daemon/server.go:650-667`), not the serving goroutine.
- Why it matters: a transient listener failure requires restarting the entire daemon and status lies in the meantime.
- Suggested fix: on non-`http.ErrServerClosed` return, log the error and clear `s.web` under `s.mu` only if it still points to the same `webState`. Coordinate with `EC-004` so a late old goroutine cannot clear a replacement listener.
- Verification: close the live listener without calling `Server.Close`, wait for `Serve` to return, assert `WebInfo()==nil`, then start a new listener; run under `-race` with count 20.
- Pitfalls: expected shutdown is not an error. Identity-check the pointer before clearing.
- Do-not: do not call `Server.Close`; socket sessions must survive web-only failure.

### EC-012 — Explicit server close leaks the context-watcher goroutine

- Severity / Area / Difficulty / Files: P2 / daemon resource lifecycle / S / `internal/daemon/server.go` (`Serve`), tests.
- Problem: every `Serve` launches `go func(){ <-ctx.Done(); s.Close() }` (`internal/daemon/server.go:616-627`). If a caller uses `context.Background()` and closes the server explicitly, the accept loop returns but this goroutine can never finish.
- Evidence: direct channel-liveness proof; `Close` has no signal consumed by the watcher.
- Why it matters: repeated embedded/start-stop use leaks one goroutine per server. Tests and long-lived supervisors are the likely trigger.
- Suggested fix: use `stop := context.AfterFunc(ctx, s.Close); defer stop()`; it allocates no permanently blocked watcher after `Serve` returns.
- Verification: add a test that repeatedly serves with a non-canceling context, closes, and uses an internal completion seam or bounded goroutine delta; run `go test -race ./internal/daemon -run TestServeCloseStopsContextWatcher -count=20`.
- Pitfalls: `AfterFunc` can race with the deferred stop; `Close` is idempotent, so that is acceptable.
- Do-not: do not require callers to cancel after close.

### EC-013 — JSON request bodies have no read deadline

- Severity / Area / Difficulty / Files: P2 / web resource security / M / `internal/daemon/web.go`, `internal/daemon/webcmd.go` (`readWebBody`), tests.
- Problem: the HTTP server sets only `ReadHeaderTimeout` (`internal/daemon/web.go:123-126`). `MaxBytesReader` bounds bytes, not time, so both decoder calls at `internal/daemon/webcmd.go:59-78` can block forever on a client that declares a body and dribbles or stops. A global `ReadTimeout` is unsuitable because SSE is long-lived.
- Evidence: standard-library semantics plus direct control flow; no request-scoped deadline is set anywhere in `readWebBody`.
- Why it matters: any authenticated client, or any client when auth is explicitly disabled, can retain connections and goroutines indefinitely.
- Suggested fix: set a short request-body read deadline via `http.NewResponseController(w).SetReadDeadline` around decoding and clear it afterward. Keep the SSE route untouched.
- Verification: raw-TCP test sends valid authenticated POST headers plus a partial body, then stalls and observes close/error within a test-shortened deadline; also prove an SSE stream survives beyond that duration. Run `go test ./internal/daemon -run 'TestWeb.*(BodyDeadline|SSE)' -count=1`.
- Pitfalls: do not set `http.Server.WriteTimeout`; it will kill SSE. Map timeout to a useful 408 when headers are still writable.
- Do-not: do not add a global request timeout middleware around streaming routes.

### EC-014 — Detached command timeout is not a ceiling and can overflow

- Severity / Area / Difficulty / Files: P2 / shell resources / S / `internal/tools/exec.go` (`bashTool`, `runBackground`), tests.
- Problem: arbitrary positive seconds are multiplied into `time.Duration` without bounds (`internal/tools/exec.go:339-350`). `runBackground` accepts every positive result (`:440-466`) although `BackgroundTimeout` is documented as the 30-minute ceiling (`:678-680`). Very large integers can overflow to a nonpositive duration and silently become the default; other values create tasks lasting years.
- Evidence: arithmetic/control-flow proof. Existing lifecycle tests cover requested short timeouts and the default, not the upper bound.
- Why it matters: a model-produced value can defeat the resource ceiling and leave detached processes mutating the workspace far beyond expectation.
- Suggested fix: validate seconds before multiplication. For background work, reject or clamp values above `int(BackgroundTimeout/time.Second)`; expose the same maximum in the JSON schema. Prefer rejection so the model sees its mistake.
- Verification: add tests for 1 second, exactly 1,800, 1,801, `math.MaxInt`, and zero/default; run `go test ./internal/tools -run 'Test.*Background.*Timeout' -count=1`.
- Pitfalls: validate before `time.Duration(a.Timeout) * time.Second`; checking the duration afterward is too late.
- Do-not: do not make detached commands inherit the turn context; outliving the turn is intentional.

### EC-015 — Resource and prompt adapters bypass MCP timeout/reconnect policy

- Severity / Area / Difficulty / Files: P2 / MCP lifecycle / M / `internal/mcp/features.go`, `internal/mcp/mcp.go`, tests.
- Problem: `readResource`, `listResources`, and `getPrompt` call `s.currentSession()` directly (`internal/mcp/features.go:68`, `:90`, `:130`). Ordinary tool calls enforce the server timeout, lazy reconnect, transport ping, and one retry in `internal/mcp/mcp.go:545-600`. The capability adapters therefore have materially weaker behavior despite appearing as ordinary tools.
- Evidence: direct path comparison. The prior `docs/mcp_gaps.md` closure covers content adaptation, not parity with the later hardened call path.
- Why it matters: a wedged capability endpoint can hold a turn until manual cancellation, and a dead server may stay unusable while the same server's normal tools recover.
- Suggested fix: extract a small helper that computes the bounded context and ensures/retries a live session, then use it for normal calls and all three capability operations. Keep operation-specific result mapping separate.
- Verification: an in-process MCP test server should block a resource/prompt request past a 20 ms configured timeout and produce a named timeout; a transport-death test should prove one reconnect. Run `go test -race ./internal/mcp -run 'Test.*(Resource|Prompt).*(Timeout|Reconnect)' -count=1`.
- Pitfalls: `listResources` paginates; one overall deadline should bound the whole list, not reset on each page.
- Do-not: do not duplicate the reconnect state machine inside each closure.

### EC-F-001 — Truncated live snapshots cannot page to discarded history

- Severity / Area / Difficulty / Files: P2 / web history / S / `internal/daemon/server.go` (`fitServerFrame`), tests.
- Problem: the protocol explicitly includes `Snapshot.Oldest` so web can page immediately before a truncated live snapshot (`internal/daemon/protocol.go:252-259`). `fitServerFrame` repeatedly drops the oldest half and sets `Truncated`, but never increments `Oldest` (`internal/daemon/server.go:2210-2227`). The browser therefore receives `oldest: 0`, for which the history API correctly returns no earlier page (`internal/daemon/webapi.go:152-172`).
- Evidence: disposable `TestReviewTruncatedSnapshotReportsOldestIndex` forced fitting and failed with `oldest=0`: `go test ./internal/daemon -run TestReviewTruncatedSnapshotReportsOldestIndex -count=1 -v`.
- Why it matters: history pagination exists and is in scope, but the exact large live sessions that need it cannot reach their discarded prefix.
- Suggested fix: track the original shaped-message index while slicing. Each drop increments `s.Oldest` by the dropped count; if the last message is also removed, `Oldest` must equal the original length. Ensure web SSE uses the fitted/bounded snapshot path as well; currently `sseFrame` directly marshals `sess.snapshot()` and can emit an unbounded frame.
- Acceptance criteria: (1) every truncated snapshot has `0 < Oldest <= original message count`; (2) requesting `/messages?before=<Oldest>` returns the adjacent older page without overlap; (3) socket and SSE initial snapshots obey a finite byte cap; (4) a nontruncated snapshot keeps `Oldest==0`.
- Verification: add the unit repro plus an HTTP integration test with oversized history; run `go test -race ./internal/daemon -run 'Test.*(Snapshot|History|WebEvents)' -count=1`.
- Pitfalls: `Oldest` is an index in the **shaped** message list, after hidden/system/empty filtering. Do not use raw provider-message indexes.
- Do-not: do not enlarge `MaxServerFrameBytes` or embed the full durable log in SSE.

No other missing web-v1 feature is reported. Web Push, todo/memory web surfaces, history search, delete, worker kill/rename, multi-user operation, TLS termination, and a service worker are explicitly deferred in `docs/plan-web.md:464-474`; roster-only lifetime and no web delete endpoint are documented decisions in `README.md` and the same plan.

### EC-I-001 — Cold model-catalog requests stampede every provider

- Severity / Area / Difficulty / Files: P3 / web models / S / `internal/daemon/webcmd.go` (`webModelsCache`, `webAPIModels`), tests.
- Problem: cache check and provider fetch are separate critical sections (`internal/daemon/webcmd.go:467-492`). Concurrent cold or just-expired requests all miss, unlock, and each run `webFetchModels`, multiplying network calls and five-second timeout goroutines.
- Evidence: direct synchronization proof; `webModelsCache` has no in-flight state.
- Why it matters: several browser tabs opening the picker together can hammer Ollama/remote catalog endpoints and return inconsistent snapshots.
- Suggested fix: add a cache-local in-flight channel. The first miss fetches; later misses wait for its completion or their request context, then read the stored result. This needs no `singleflight` dependency.
- Verification: concurrently issue 20 `/api/models` requests against a counting fake provider; assert one upstream catalog call and identical results. Run `go test -race ./internal/daemon -run TestWebModelsSingleFlight -count=10`.
- Pitfalls: never hold the cache mutex during network I/O; close the in-flight channel on all paths.
- Do-not: do not add `golang.org/x/sync/singleflight` for this one field.
